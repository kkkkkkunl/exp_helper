# 记录与归档规则

## 记录

**R-01** 一次实验执行对应一份记录。项目、实验方案、样本是三个独立关联概念，不要混为一层。

**R-02** 目录结构固定：

```
项目/实验/<实验编号>/
├── 实验记录.md
├── 原始附件/
├── 汇报.pptx
└── results/<结果项编号>/
```

**R-03** 实验编号 = 首次创建时的北京时间 `YYYYMMDD-HHmmss`，创建后固定。补录、重新整理沿用原编号。同秒新建时由 `allocate_id.py` 等待下一秒，不要手工造号。

**R-04** 实际实验日期单独记录。**列表排序用实际日期，不要用编号排序**——补录的编号是创建时间，和实验发生顺序不一致。

**R-05** 记录核心字段：实验编号、日期、目的、实验方案、结果、附件。

**R-06** 实验方案是**一级分区**，内含参考方案与实际实验方法两个子部分。

**R-07** 实验方法只写实际操作，尽量简洁。不重复比较计划与实际——例如只写"孵育 45 分钟"，不要写"计划 30 分钟，实际 45 分钟"。

操作前计算另在 `## 上样计算` 展示输入、单位、skill 依据与拟用量，经阶段确认或暂停保存写入。该部分不冒充实际方法或实测结果，实际量按用户实际操作记录，不由计算自动代填。

**R-08** 创建实验时固定模板内容与版本来源，元信息记下来源。后续模板变更只影响新实验，除非用户明确要求更新本次。

**R-09** 目的从用户输入、提供的方案或已有项目资料中提取并简化。**不推断研究意图**。缺失时询问，并继续其他整理。

**R-10** 疑问与待补信息保存在交互状态，不写入最终记录的已执行方法。普通回答保持会话草稿；明确暂停保存后，后续内容直接进入日历，不另建待办.md；各步骤保留实际执行状态。

**R-11** 用户在对话中明确提供的内容优先于图片、附件和旧记录。发现冲突仍在对话里确认。

**R-12** 记录能逐项核对、能找回原始材料、能发现遗漏。重复运行不产生重复记录、不覆盖人工修改。

已有记录的正文或受管属性经授权发生变化时，先将完整旧版保存在项目根 `history/<实验编号>_<YYYYMMDD-HHMMSS-ffffff>.md`，修改时间为本次确认保存的北京时间；首次保存、内容不变、纯会话重算和同一动作重试不新增历史。转换受管附件引用以适应历史位置，原附件不重复复制，历史关联原实验归档。既有内部历史与 OpenSpec 的 hisotry 保留各自用途。

## 归档

**R-13** 原始材料保持内容及文件名，移动到 `原始附件/`，记录中的链接指向归档后的文件。

归档是破坏性操作，脚本按"复制 → 校验 sha256 → 删除源"执行，校验失败不删源。

**R-14** 目标同名或同内容已存在时：暂停该项并在对话中提示，不自动改名、不自动覆盖、不自动合并。其余文件继续归档。

**R-15** 同名冲突与"内容相同的重复上传"要区分：

- 同名不同内容 → 必须由用户决定保留哪个
- 不同名但内容相同 → 提示可能是重复上传，问用户是否仍需保留

## 人工修改

**R-16** 已生成的记录或 PPT 有人工修改时，**先展示拟更新内容，确认后再合并**，不直接覆盖。

判断是否被改过：文件内容的哈希与上次写入记录不一致即视为被改过。脚本不自动合并，合并由模型读取差异后向用户确认。

## 核对清单

交付前逐项过一遍：

- [ ] 编号与目录一致，实际实验日期已填写
- [ ] 目的来自用户或已有资料，不是推断的
- [ ] 实验方案含参考方案（含模板版本）与实际实验方法
- [ ] 方法只写实际操作，没有计划/实际对照表
- [ ] 结果里的数值都有出处，没有从模板生成的结果
- [ ] 附件全部在 `原始附件/`，链接可点开
- [ ] 记录里没有疑问句、待办、TODO
- [ ] 库存清单已获用户确认并提交
- [ ] PPT 的结论与后续计划能追溯到用户原文
